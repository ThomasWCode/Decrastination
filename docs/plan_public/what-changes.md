# What would have to change

An inventory of the app as it is on 31 Oct 2026 (4.10.0, versionCode 96; the widget 0.5.1) against what a public release needs, area by area. Each row says what's there, what the public version needs, why, and which of the owner's decisions it reverses or bends; a decision reversed is the owner's call, not the plan's ([decisions-needed.md](decisions-needed.md)). The rules the product keeps whatever changes are in [niche.md](niche.md) §The rules a public version keeps. The order of building is in [stages.md](stages.md).

**Severity**: **blocks** (nothing can ship without it), **needed** (needed before a stranger installs it), **later** (after the first users), **keep** (right as it is).

## Protection and the parent

Protection's six layers (spec/blocking-and-protection.md §Protection) are the part of the app the stores touch most. On Play two of them are prohibited uses (the settings guard and the device admin, above), so the product's protection is **four layers and a witness**: no bypass button in the app (1), loosening that waits (4), a watchdog that warns (5), the parent's code (6), and the parent account told when blocking is switched off or the app removed. Protection stays "friction, not security" as the spec already says; what changes is that the friction is social where it was mechanical. On iOS, Family Sharing's `.child` authorisation gives back the lock Android can't ([compliance.md](compliance.md) §iOS).

| | Today | For a public release | Why | Severity |
|---|---|---|---|---|
| No bypass (D-45) | No override button; the service can't be switched off while armed (the guard) | No override button, as now; the service **can** be switched off in Settings, and the app notices at once (its disconnect, the half-minute check), records it, and the parent account is told, by a notification or in the week's summary (Q141) | Play forbids stopping the user; it doesn't forbid telling someone they chose. Freedom's Android product works this way | blocks |
| The parent code | A TOTP secret shown once as a QR for "your dad's authenticator" (the wording in `ProtectionActivity.kt`, `Protection.kt`), the owner's first name as its default label (`Totp.kt`) | A **parent account** on the server holding the code's secret, with the words generic ("a parent or carer"); the QR still works for a parent who wants an authenticator; the phone verifies offline (plan_web W-19) | The owner's family in the strings; a product's parent needs an account to recover a lost authenticator | blocks |
| The 24-hour wait (D-46) | Counted on the phone's uptime clock | Counted by the server once the state is shared (plan_web W-23); shown to the parent | A product with a server shouldn't rely on a clock the student holds | needed |
| The watchdog (layer 5) | Repairs the service with `WRITE_SECURE_SETTINGS`; warns on the widget and a notification | Warns the student and tells the parent account; never repairs | The permission can't be granted without adb | blocks |
| The summary (D-66) | An email the student sends by hand, in the third person, to an address set on the phone | Kept as the parent's view, delivered to the parent account weekly with the student's one-tap send, never automatically (D-66); gains a line on the blocker's state (armed, off since, changes waiting) | The one window the parent gets, and the student's hand on it is the point | keep |
| Arming | A wizard: device admin, the QR, *Arm now?* | The same without the device admin; the parent account pairs by a code; the student is shown exactly what the parent will see | | needed |
| What's guarded (D-46) | Only loosening | Unchanged | | keep |
